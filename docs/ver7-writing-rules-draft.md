# 日誌と memory の書き方の規則(Ver7.0 下書き)

**状態: 承認済み(2026-11-22、ふらる)。決定: D1(具体的な要素の無い行)は残す。M1(日付の無い項目)は、弱い警告のまま(必須にはしない)。** 2026-11-22、Phase 1-C(設計書の「書き方の規則」、企画書 P-15)。
実装は、承認された条件の一覧を、サーバーが保存・追記のときに「警告」として返す(Phase 3)。切り替えは移行の日。それまでは、v6.2の規則(`_system/CLAUDE.md`)のまま。

方針(2026-11-22、ふらる): **長さの上限で削るのではなく、中身のある、情報密度の高い文であることを重視する。** 残したい情報が、上限のために削られることがあってはならない。

## 1. 分担

| 置き場 | 書くこと | 性質 |
|---|---|---|
| 日誌(`journal`) | その日にやったことと、起きたこと | 追記だけ。過去の節は書き換えない |
| memory | いま有効な状態、やること、申し送り・待ち | いま有効な分だけ。丸ごと書き直す |
| 記事(`resource`・決定の記録など) | 詳細・背景・手順・設計 | memory・日誌から参照する |

残りの作業と申し送りは、**日誌に書かず、memory に書く**。詳細が長くなるときは、memory を長くするのではなく、**別の記事に置き、memory からは1行で参照する**。

## 2. 日誌の書き方

1. **1回の追記は、1つの作業のまとまり**(1つの節)。見出し(`## HH:MM 端末・AI`)はサーバーが付ける。手で書かない。
2. 節の中の見出しは、`###` から始める。
3. 本文の型として、次を**勧める**(守らなくても、警告は出さない):
   - `### 背景`(任意): なぜ、その作業をしたか。
   - `### やったこと`: 何を、どうしたか。
   - `### 起きたこと`: 判断とその理由、つまずき、結果。
   - `### 気づき・教訓`(任意): 次に生かすこと。
4. **書くこと**: やったこと、起きたこと(判断の理由・つまずき・気づき・教訓)、確認の結果。
5. **書かないこと**: 残りの作業・申し送り(→ memory)、コマンドの出力やコードの写し(要点だけ書き、長いものは記事かファイルを参照する)、memory にある内容の再掲(参照する)。
6. 直したいとき: 既存の節は書き換えられない。訂正は、新しい節として追記する。全体を直したいときだけ、通常の保存(版つき)で書き直す。

## 3. memory の書き方

1. 節の構成は、これまでどおり: `概要`・`約束事`・`現在の状態`・`やること`・`申し送り・待ち`。
2. 項目は、**1項目1行・1つの事実**。
3. 「やること」「申し送り・待ち」の項目は、**末尾に日付 `(11/22)`** を付ける(いつから残っているかが分かる)。
4. **長さの上限は設けない**(字数・行数・1項目の長さ、いずれも)。保存の結果に、大きさを表示するだけ。
5. 詳細が増えたら、別の記事(`resource` など)に移し、memory には**参照を1行**で残す。
6. 完了した項目は、memory から外してよい。**外した項目は、サーバーが日誌へ自動で記録する**(§6)ので、失われない。

## 4. 密度の規則(日誌・memory 共通)

良い1行は、次を満たす。

1. **具体的**: ファイル名・関数名・ID・数値・日付・コマンドのどれかを、1つ以上含む。「何が・どこで」が分かる。
2. **結論と根拠**、または**状態と次の条件**が書かれている。「確認した」「対応した」だけで終わらない。
3. **1行に1つの事実**。
4. 曖昧語を単独で使わない(「いろいろ」「適宜」「問題なし」「対応した」「確認した」)。
5. 別の場所にある内容を**再掲しない**(日誌 ↔ memory は、参照で示す)。

**例**

| 悪い | 良い |
|---|---|
| いろいろ直した。 | `library_store` の `journal.rs` で、先頭の BOM を本文に残さないようにした(PowerShell の `Set-Content -Encoding utf8` が付けるため)。 |
| 試験は問題なかった。 | 通し試験 `e2e.py` が 29/29 件で通った。変更前のバイナリとの比較も一致(エラーのパスだけ相対)。 |
| サーバーの作業を進める。 | Phase 2: `services/shiori-proto-server` の窓口を本番の形にする(11/22) |

## 5. 警告の条件の一覧

**すべて警告であり、保存は止めない。** 警告は、保存の結果の `warnings` に、理由と該当の行つきで返る。しきい値は、実際の記事(journal 168件・memory 17件)に当てて調整した(§8)。

| ID | 対象 | 条件(機械で判定できる形) | 重さ |
|---|---|---|---|
| J1 | 日誌 | 節の本文の見出し(`###` 以下)が、「申し送り・残りの・残り作業・未完了・やること・TODO・次にやる」**で始まる**(途中に含むだけでは、警告しない) | 通常 |
| J2 | 日誌・memory | **子の節を持たない**節の本文(見出しを除く)が30字未満。「なし」「未定」で始まる節は、除く | 通常 |
| J3 | 日誌 | 節の本文に `#`・`##` の見出しがある(階層が崩れる) | 通常 |
| D1 | 日誌・memory | 具体的な要素(下記)の無い行が、**5行以上で、かつ7割以上** | 弱い |
| D2 | 日誌・memory | **25字以下**で、曖昧語(いろいろ・色々・適宜・問題なし・特になし・その他・対応した・いい感じ・ちゃんと)を含み、具体的な要素が無い行 | 弱い |
| D3 | 日誌・memory | 1行に事実が詰め込まれている: **句点(。)が6つ以上**、または**300字を超えて句点が2つ以上** | 弱い |
| D4 | 日誌・memory | **重複**: 同じ記事の中で、同じ行(記号・空白を除いて同一)が2回以上。**再掲**: 日誌の行が、同じプロジェクトの memory の行と、**文字2つの切り出しの類似度が0.6以上** | 通常 |
| M1 | memory | 「やること」「申し送り・待ち」の項目に、**日付 `(m/d` が、どこにも無い**(「なし」「未定」で始まる項目は除く) | 弱い |

**具体的な要素**(D1・D2 の判定): 次のどれか1つ以上を含む。
- 2桁以上の数字、または日付(`11/22`・`2026-11-22`)。
- バッククォートで囲まれた語(`` `名前` ``)。
- 拡張子つきのファイル名、`a/b` の形のパス。
- ID・ハッシュ(英数字が混ざった6文字以上の語)。
- コマンド(`cargo test` のように、半角の語が2つ以上続くもの)、関数名らしい語(`foo_bar`・`fooBar`・`foo()`)、大文字の略語。

**警告にしないもの**(機械では判定しない): 内容が本当に重要か、理由が正しいか、型(背景・やったこと…)を使っているか。これは、§7 の自己点検と、あなたの確認に任せる。

**既知の弱点**: D1 は、企画・方針の整理のような**抽象的な内容の日誌**を、誤って拾う(具体的な語が、もともと少ないため)。そのため、「弱い」警告にし、5行・7割と、厳しめにした。

## 6. 外した項目の自動記録(memory)

memory を保存するとき、サーバーが前の版と比べ、**消えた項目**を日誌に残す。
- 対象: 前の版にあって、新しい版に無い項目(`- ` の行)。ただし、書き換えられた項目(新しい版に、文字2つの切り出しの類似度が0.6以上の行がある)は、除く。
- 記録先: そのプロジェクトの、その日の日誌に、節として追記する。
  ```
  ## HH:MM 端末・AI

  ### memoryから外した項目

  - (外した行をそのまま)
  ```
- 全体用の memory(`memory-global`)は、全体の日誌(`10-common/journal`)へ。
- 目的: 本来残したい情報が、整理のときに、誤って失われないようにする。いまの退避(3世代)と違い、**期限なく残る**。

## 7. AI の自己点検の一覧(`session-close` などの手順書に入れる)

書いたあと、保存する前に、次を確かめる。

1. 日誌の節: 「やったこと」に、**ファイル・関数・数値・コマンド**のどれかが入っているか。
2. 「起きたこと」に、**判断の理由**、または**つまずきの原因と対処**が書かれているか。
3. 残りの作業・申し送りが、日誌に混ざっていないか(あれば memory へ)。
4. memory の項目が、1行1事実で、**末尾に日付**があるか(「やること」「申し送り・待ち」)。
5. memory から項目を外すとき、**詳細が日誌か記事に残っている**か(外した項目は自動で日誌に記録されるが、詳細が別の記事にあるなら、参照を1行残す)。
6. 同じ内容が、日誌と memory の両方に、書かれていないか。

## 8. 測定の結果(2026-11-22。実機のlibrary、journal 168件・memory 17件、読み取りだけ)

**いまの記事に当てたときの、警告の出方**(調整後の条件)

| 条件 | 日誌(168件) | memory(17件) | 所見 |
|---|---|---|---|
| J1 申し送りの混入 | 0件 | - | 分担は、ほぼ守られている。最初の条件(見出しに「含む」)は、「memoryの「やること」を確かめた」のような見出しを誤って拾ったので、「始まる」に直した |
| J2 中身の無い節 | 0件 | 1件(「やること」が「なし」のみ) | 最初の条件は、親の見出しの直後に子の見出しが続く記事を、誤って25%も拾った。子の節を持たない節だけに直した |
| D1 具体的な要素の無い行 | 4件(2%) | 0件 | 4件は、企画・方針の整理の日誌。**誤検出の型**(弱い警告にとどめる理由) |
| D2 曖昧語だけの行 | 1件 | 0件 | 「問題なしの回答だった」という具体的な文を拾った。曖昧語を絞り、25字以下に狭めた |
| D3 1行に詰め込み | 行の1%(45行) | 行の1%(6行) | 最初の「句点3つ」は、日誌の記事の91%を拾った(日本語では普通の長さ)。「句点6つ以上・300字超」で、行の1%に絞った |
| D4 同じ記事の中の重複 | 0件 | 0件 | |
| D4 再掲(類似度0.6以上) | 4件(2%) | - | 日誌の行と、memory の行が、ほぼ同じ内容。再掲として妥当 |
| M1 日付の無い項目 | - | 4つの memory・8項目 | 「解決済み」の注意書きや、状態だけの項目。日付がある項目は、どこにあっても、数えない |

**検出力の確認**(人工の悪い例): 曖昧な日誌(J2・D1・D2)、申し送りの混入(J1)、中身の無い節(J2)、同じ行の繰り返し(D4)、memory の再掲(D4)、詰め込み(D3)は、すべて拾えた。具体的な日誌は、警告なし。

**確定していないこと**
- D1 を残すか、やめるか(誤検出の型があるため。残すなら、保存結果に控えめに表示)。
- しきい値は、新しい書き方で記事が増えてから、もう一度測って調整する(いまの記事は、旧 journal を1回の追記とみなして当てたもの)。
- 規則の文章は、`_system/CLAUDE.md` の改訂として、移行の日に切り替える(それまでは、v6.2の規則)。
