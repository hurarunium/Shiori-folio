## なぜこのskillが必要か

作業再開時に前回の状態を思い込みで進めると、他の場所・他の手段(手動操作、別のAIセッションなど)で行われた変更を見落として事故につながる。また、複数タスクをまたいだ文脈(前回何をしていたか、今日何をやる予定か)を毎回一から思い出すのは非効率である。`session-close`が作業に区切りをつける際の「後片付け・振り返り・記録」を担うのに対し、このskillはその対称として、作業に入る際の「状態確認・文脈の引き継ぎ・準備」をまとめて行う。

## いつ使うか

ユーザーが「作業を開始します」「始めます」のように、作業に着手する意思を明示したタイミングで使う。時刻や経過時間による自動判定は行わない。

## 手順

### 1. git状態の調査

以下を実行し、現在の状態を把握する。思い込みで前回の状態のまま進めない。

0. 作業ディレクトリ自体がgit管理外の場合は、配下のサブディレクトリに`.git`がないか確認し、あればそちらを対象リポジトリとして以降を行う
1. `git status`で作業ツリーの状態(未コミットの変更、未追跡ファイル)を確認する
2. `git log --oneline -10`程度で直近のコミット履歴を確認し、見覚えのないコミットが増えていないか確認する
3. `git fetch`してリモートとのahead/behindを確認する。behindしている場合は`git pull`が必要かどうかをユーザーに確認する
4. `git fetch`が失敗した場合(SSH認証エラーなど)は、それを軽微な注記として流さず、作業開始の前提が崩れるブロッカーとして扱う。失敗の原因を調査してユーザーに明示し、「リモートの更新有無を確認できないまま作業を進めてよいか」を確認してから先に進む

### 2. 前回内容の把握

詩織のセカンドブレイン(library)と、`completion-report`/`session-close`で残した記録を読み込み、前回何をしていたか・何が未完了だったかを把握する。詩織は特定のAI・PC・メモリに依存せず、新環境や新規AIでも同じ引き継ぎができることを目的に作られている。そのため、各AIが独自に持つ記憶(自動メモリ)の有無に関わらず、毎回このステップで必ずlibraryから前回内容を把握する。

**Ver7.0では、libraryの正本は、余りのPCで動くサーバーにある**(SSDは、バックアップ専用)。端末からは、詩織のMCP(`search_library`・`list_documents`・`read_document`)と、CLI(`shiori-task`)で読む。**SSDやサーバーのファイルを、パスで直接読まない。** パスは `library/…`・`knowledge/…`・`tasks/…` の形で、検索結果の `path` や `list_documents` の結果を、そのまま `read_document` に渡す。作業ディレクトリ配下の `library/` は開発用の空ライブラリなので、記録の探索には使わない(`library/_system/CLAUDE.md`参照)。

1. **対象プロジェクトを特定する**: 作業ディレクトリ・gitリポジトリ名・会話の文脈から、対象の`project` idを判断する。候補は `read_document` で `library/_system/projects.yaml` を読んで確認する(全体に関わる作業は `common`)。判断できない場合はユーザーに確認する。
2. **共通記憶MD(memory)を読む**: 次を `read_document` で実際に読む。
   - 全体用: `library/10-common/memory-global.md`
   - 対象プロジェクトの`memory.md`: `library/20-projects/{project}/memory.md`(`search_library`でproject名を検索すると先頭に返る)
   - タスクの一覧: `shiori-task list`(全プロジェクトの未完了タスク。締切つき)

   memoryの「現在の状態」「やること」「申し送り・待ち」は、**いま有効な分の正本**。以降の探索(3〜5)は、memoryに書かれていない詳細を補うために行い、memoryと食い違う記録が見つかったら、最初の返答で指摘する。読んだ時点の`updated`の値を控える(`session-close`でmemoryを更新するときの`--expect-updated`に使う)。対象プロジェクトのmemoryが無いときは、その旨を伝え、既存の日誌から初版を作るかをユーザーに尋ねる。
3. **そのプロジェクトで検索する**: `get_context_profile`を呼んだうえで、`search_library`をプロジェクト名・主要なキーワードで検索する。「作業記録」「前回」「セッション」のような汎用語だけで検索しない(他プロジェクトの記録が混ざり、対象の記録が埋もれる)。1回の検索で済ませず、必要なら語を変えて複数回検索する。
4. **日誌で、最新を判定する**: 検索結果の並び順は意味的な近さであり、新しさではない。日誌は日付ごとのファイル(`YYYY-MM-DD.md`。**日の区切りは午前5時**で、午前0〜5時の作業は前の日の日誌に入る)なので、次で最新を確かめる。
   - `list_documents` で `library/20-projects/{project}/journal` を開く(新しい日付の順に返る)。先頭から、直近の1〜3件を読む。
   - 全体の日誌 `library/10-common/journal` の、最新の1件も読む。先頭の `## 目次` に、各プロジェクトの直近の作業が、1行ずつ(`- HH:MM [project] 要約`)出ている。
   - 日誌以外の記事(`resource`・`decision` など)は、`search_library`(project指定。経緯モードで、新しい順)で確かめる。企画書や落とし穴の記録は、`resource`に置かれることが多い。macOSの`._`で始まるものは無視する。
5. **直近の記録を読む**: 日誌は、節(`## HH:MM 端末・AI`)ごとに、**いつ・どの端末の・どのAIが**書いたかが分かる。見出しだけで判断せず、直近の節を実際に読む。
6. **gitの履歴と突き合わせる**: ステップ1のコミット日付(`git log --format='%h %ad %s'`)と、日誌の節の日時を比べ、コミットされているのに記録がない作業がないか確認する(午前0〜5時の作業は、前の日の日誌に入る点に注意)。記録がない場合は、探し方が不十分でないか(上記3〜4)を先に疑ってから、「記録なし」とユーザーに伝える。
7. **サーバーと、端末のCLIの版を突き合わせる**: 実機(SSD)への配置の代わりに、サーバー(`shiori-server`)と、各端末のCLI・アプリが、直近のコミットの版で動いているかを確かめる。コミット済みなのに未配置のものがあれば、最初の返答で伝える(解消するまでの管理は、memoryの「やること」に書く)。配置先の一覧と注意は、library内の`deploy-and-verify-pitfalls-20261008`(Ver7.0の手順へ更新する)にある。
8. **進行中の企画書・設計書と実装フェーズを確認する**: memoryや直近の記録に未完了作業がある場合、対象プロジェクトの`resource`から該当する企画書・設計書を探して(`search_library`)本文を `read_document` で読む。設計書にフェーズがある場合、記録・memory・git status/logを照合し、完了済みの最後のフェーズと次に取り組むフェーズを特定する。コミットの有無だけを根拠にフェーズ完了と判断しない。資料間で状態が食い違う、または完了条件の達成が確認できない場合は、食い違いと不明点をユーザーに示し、推測で再開位置を決めない。
9. **最初の返答に含める**: 「memoryの現在の状態」「memoryのやること・申し送り・待ち」「前回やったこと(直近の日誌)」「サーバー・CLIの未配置のもの(あれば)」「ほかのプロジェクトの直近の動き(全体の日誌の目次から。あれば)」に加え、該当する場合は「進行中の企画書・設計書」「完了済みの最後のフェーズ」「次に取り組むフェーズ」を、ユーザーが尋ねる前に伝える。タスクの一覧に、締切を過ぎたものや7日以内のものがあれば、それも伝える。残りの作業と申し送りの正本はmemoryで、日誌には書かれていない(日誌は、やったことと起きたことだけを持つ)。

- **詩織のサーバーにつながらない場合**は、このステップ(memoryを読むことを含む)をスキップし、黙って進めず、その旨を伝え、続行してよいか確認する。つながらない理由(サーバーの停止、Tailscaleの切断、`data/server.json` の不備、トークンの失効)を、わかる範囲で示す。**手元のSSDや古いコピーを、代わりに読まない**(正本が2つあるように見えてしまうため)。
- 上記を尽くしても記録が見つからない場合は、探した範囲(検索語・開いたフォルダ)を示したうえで、ユーザーに直接確認する

### 3. 今日やることの整理

上記1・2で得た情報(特にmemoryの「やること」と「申し送り・待ち」)をもとに、今日何をするかをユーザーと相談しながら整理する。憶測で優先順位を決めつけず、ユーザーの意向を確認する。

### 4. 開発サーバーの起動(Web開発系のみ)

対象プロジェクトがWeb開発系(`package.json`、`astro.config.*`など)であれば、`run` skillを使って開発サーバーを起動し、プレビューを表示する。Web開発系でなければこのステップは省略する。
